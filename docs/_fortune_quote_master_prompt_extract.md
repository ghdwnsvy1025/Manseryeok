# 오늘의 운세·오늘의 명언 콘텐츠 확장 마스터 프롬프트

이 프롬프트는 기존의 “사주 기반 개인화 일기 앱 개편 마스터 프롬프트”에 추가되는 확장 요구사항이다.

기존에 정의한 다음 시스템을 삭제하거나 약화하지 마라.

* 오늘의 질문 생성 알고리즘
* 상태 체크 UI
* 사용자 직접 입력 우선 원칙
* 사주 규칙 기반 사전확률
* 최근 상태 분석
* 일주 계층형 개인 통계
* 자유 일기 텍스트 분석
* 과거 일기 재분석
* 동적 가중치
* 질문 피드백
* RAG 역할 제한
* Ridge 섀도 비교
* 데이터 누수 방지
* 규칙·모델·프롬프트 버전 관리
* 관리자 디버그 기능

이번 작업에서는 기존 구조를 공통 기반으로 확장하여 다음 세 가지 콘텐츠를 유기적으로 연결한다.

1. 오늘의 질문
2. 오늘의 운세
3. 오늘의 명언 또는 오늘의 문장

---

# 1. 제품의 하루 경험 구조

하루 사용자 경험을 다음 순환 구조로 설계한다.

## 아침 또는 첫 앱 진입

1. 오늘의 질문을 보여준다.
2. 오늘의 종합 운세를 짧게 보여준다.
3. 사용자가 원하는 경우 분야별 운세를 펼쳐서 볼 수 있다.
4. 상태 체크 또는 일기 작성으로 자연스럽게 이동시킨다.

## 상태 체크 및 일기 작성

1. 행복도, 기분, 핵심 상태, 사건 태그를 기록한다.
2. 오늘의 질문을 일기 입력창 주변에서 다시 확인할 수 있게 한다.
3. 사용자는 질문에 직접 답하거나 자유롭게 일기를 쓸 수 있다.
4. 질문에 답하는 것을 강제하지 않는다.

## 일기 저장 직후

1. 저장 완료 피드백을 보여준다.
2. 오늘 기록과 어울리는 실제 명언 또는 앱이 만든 오늘의 문장을 공개한다.
3. 명언의 출처와 작가를 함께 보여준다.
4. 사용자가 명언을 저장하거나 공유할 수 있게 한다.
5. 질문 적합도와 명언 만족도 피드백은 선택적으로 제공한다.

## 다음 날 이후

오늘 입력된 상태와 일기, 질문 피드백, 운세 반응, 명언 반응은 다음 날 이후 개인화에 사용한다.

오늘의 질문과 오늘의 운세가 생성된 뒤 입력된 오늘 데이터는 해당 질문과 운세의 생성 결과를 변경하면 안 된다.

# 2. 공통 Daily Insight Context

오늘의 질문과 오늘의 운세가 서로 다른 알고리즘을 독립적으로 실행하지 않게 한다.

두 콘텐츠가 공통으로 사용하는 `DailyInsightContext`를 먼저 생성한다.

예시 구조:

```json
{
  "user_id": "user-id",
  "event_date": "YYYY-MM-DD",
  "timezone": "Asia/Seoul",
  "data_cutoff_at": "ISO-8601 datetime",
  "recent_state": {
    "keyword_scores": {},
    "trends": {},
    "confidence": 0.0
  },
  "day_pattern": {
    "day_pillar": "",
    "keyword_scores": {},
    "domain_scores": {},
    "confidence": 0.0
  },
  "natal_prior": {
    "default_strategy": {},
    "overuse_risk": {},
    "regulation_resource": {},
    "confidence": 0.0
  },
  "question_preference": {},
  "content_history": {},
  "overall_confidence": 0.0,
  "engine_version": ""
}
```

`DailyInsightContext`는 해당 날짜 상태 체크 이전에 생성한다.

다음 데이터만 사용할 수 있다.

* 전날까지의 상태 기록
* 전날까지의 일기
* 전날까지의 질문 피드백
* 전날까지의 운세 피드백
* 전날까지의 명언 반응
* 오늘의 일주
* 사용자 원국
* 온보딩 답변
* 전체 사용자 기준 통계

오늘 입력값은 사용하면 안 된다.

오늘의 질문과 오늘의 운세는 동일한 컨텍스트를 사용하되 표현 목적만 달라야 한다.

* 오늘의 질문: 가장 중요한 한 가지 주제에 집중
* 오늘의 운세: 여러 생활 영역으로 분해해 종합적으로 설명

컨텍스트를 날짜별로 저장하고 생성 당시의 모델·규칙·매핑 버전을 보존한다.

# 3. 오늘의 질문 역할

오늘의 질문은 기존 시스템을 유지한다.

목적:

* 한 번 멈추어 생각하게 하기
* 오늘의 핵심 심리 또는 행동 주제를 인식시키기
* 일기 작성을 시작하기 쉽게 만들기
* 지나치게 많은 내용을 전달하지 않기

출력은 기본적으로 한 문장이다.

예:

“오늘 꼭 책임지지 않아도 되는 일 한 가지는 무엇인가요?”

오늘의 질문은 운세 전체의 요약문이 아니다.

오늘 가장 중요한 `primary_keyword + tension_keyword`를 성찰 질문으로 변환한다.

---

# 4. 오늘의 운세 역할

오늘의 운세는 오늘의 질문과 동일한 공통 분석값을 사용하지만 여러 생활 영역으로 확장한다.

기본 섹션은 다음 다섯 개로 구성한다.

1. 종합운
2. 일·학업운
3. 관계·연애운
4. 재물운
5. 건강·회복운

필요하면 다음 보조 섹션을 추가할 수 있다.

* 오늘의 기회
* 오늘의 주의점
* 오늘의 한 걸음
* 결정하기 좋은 것
* 서두르지 않아도 되는 것

섹션을 너무 많이 만들어 사용자가 읽기 어렵게 하지 마라.

기본 화면에는 종합운과 각 영역의 한 줄 요약만 보여준다.

상세 설명은 사용자가 탭하거나 펼쳤을 때 보여준다.

# 6. 운세 점수 계산

각 영역 d와 키워드 k에 대해 다음 구조로 점수를 계산한다.

```text
DomainScore(d)
=
최근 상태 기여
+ 오늘 일주 개인 효과
+ 원국 조절 필요
+ 해당 영역의 과거 개인 반응
+ 신호 일치 보너스
- 반복 패널티
- 불확실성 패널티
```

기존 질문 엔진과 같은 모듈 가중치를 사용하되 영역별 키워드 매핑을 추가한다.

운세는 단순히 “좋다 또는 나쁘다”로만 분류하지 않는다.

각 영역 결과는 다음을 포함한다.

```json
{
  "domain": "work",
  "tone": "balanced",
  "score": 0.64,
  "confidence": 0.72,
  "headline": "속도보다 정리가 힘이 되는 날",
  "summary": "할 일을 더 늘리기보다 우선순위를 정리할수록 집중하기 쉬운 흐름입니다.",
  "opportunity": "이미 시작한 일을 마무리하는 것",
  "caution": "여러 요청을 한꺼번에 맡는 것",
  "action": "가장 중요한 일 한 가지를 먼저 정해보세요.",
  "evidence_codes": [],
  "engine_version": ""
}
```

점수는 사용자에게 반드시 숫자로 보여줄 필요가 없다.

점수를 보여주더라도 “운이 82점”처럼 과학적 정확도를 오해하게 만들지 마라.

권장 사용자 표현:

* 흐름이 가벼워요
* 차분한 점검이 필요해요
* 에너지 관리가 중요해요
* 관계에서 속도를 조절해보세요
* 결정 전에 한 번 더 살펴보세요

# 7. 운세 문장 생성 규칙

LLM은 영역 점수와 핵심 내용을 자연스럽게 문장화하는 역할만 한다.

LLM이 사주를 다시 해석하거나 점수를 다시 결정하면 안 된다.

다음 표현을 금지한다.

* 반드시 좋은 일이 생긴다
* 돈이 들어온다
* 연인이 생긴다
* 헤어질 운이다
* 사고가 난다
* 병이 생긴다
* 직장을 잃는다
* 계약이 반드시 성공한다
* 오늘은 무조건 나쁘다
* 운명이 정해져 있다

권장 표현:

* 가능성이 있습니다
* 이런 부분을 점검하기 좋은 날입니다
* 서두르기보다 확인하는 편이 좋습니다
* 평소보다 민감하게 느낄 수 있습니다
* 내 에너지를 먼저 살펴보세요
* 현재 흐름에서는 이런 선택이 도움이 될 수 있습니다

운세 문장은 공포보다 행동 가능성을 높여야 한다.

사용자가 실제 생활에서 적용할 수 있는 한 가지 행동을 포함한다.

# 8. 운세 콘텐츠의 길이와 UI

## 홈 화면

기본 노출:

* 오늘의 질문 카드
* 종합운 한 줄
* 분야별 운세 미리보기
* 상태 체크 CTA

권장 순서:

1. 오늘 날짜 및 인사
2. 오늘의 질문
3. 종합운 한 줄 요약
4. “오늘의 흐름 자세히 보기”
5. 상태 기록 CTA

기존 UI가 이 흐름을 자연스럽게 수용할 수 있으면 유지한다.

기존 UI가 정보 우선순위, 입력 피로 또는 모바일 가독성에서 불리하다면 수정하거나 재설계해도 된다.

새로운 UI를 적용할 때는 기존 디자인 시스템과 브랜드 정체성을 최대한 유지한다.

## 운세 상세 화면

각 영역을 아코디언 또는 카드로 구성한다.

각 카드에는 다음만 기본 노출한다.

* 영역명
* 한 줄 헤드라인
* 짧은 설명
* 펼치기 버튼

펼쳤을 때 다음을 보여준다.

* 기회
* 주의
* 오늘의 행동
* 선택적으로 “이 내용이 잘 맞나요?”

한 화면에 긴 운세 문단 다섯 개를 모두 펼쳐놓지 마라.

# 9. 콘텐츠 노출에 따른 데이터 오염 관리

오늘의 질문과 오늘의 운세는 상태 체크 전에 노출될 수 있으므로 사용자의 응답에 영향을 줄 가능성이 있다.

다음 이벤트를 저장한다.

* question_impression
* question_opened
* fortune_summary_impression
* fortune_detail_opened
* fortune_domain_opened
* checkin_started
* checkin_completed
* diary_started
* diary_completed

상태 기록 전에 어떤 콘텐츠를 봤는지 저장한다.

모델 평가 시 다음 그룹을 분리할 수 있게 한다.

* 질문만 본 사용자
* 운세 요약까지 본 사용자
* 상세 운세를 본 사용자
* 콘텐츠를 거의 보지 않고 기록한 사용자

콘텐츠를 본 뒤의 상태가 콘텐츠 자체의 영향을 받았을 수 있다는 점을 분석에서 구분한다.

# 10. 오늘의 명언 역할

오늘의 명언은 일기 저장 후 제공하는 감정적 보상 콘텐츠다.

목적:

* 사용자가 기록을 마쳤다는 느낌을 주기
* 오늘 경험을 한 번 더 따뜻하게 정리하기
* 일기 작성 후 감정적 여운 만들기
* 앱에 다시 돌아오고 싶은 기억 만들기
* 억지스러운 조언보다 공감과 위로 전달하기

오늘의 명언은 오늘 질문과 운세만으로 미리 확정하지 않는다.

일기 저장 후 다음 데이터를 결합하여 선택한다.

* 오늘의 질문 핵심 키워드
* 오늘의 운세 핵심 주제
* 사용자가 실제로 입력한 상태
* 선택한 기분
* 사건 태그
* 일기 텍스트 특징
* 직접 입력과 텍스트 추정의 불일치
* 최근 보여준 명언
* 사용자의 명언 선호
* 콘텐츠의 감정 강도
* 출처 검증 상태

# 11. 명언 수집 정책

운영 중인 사용자 요청마다 인터넷을 실시간으로 긁어서 명언을 보여주지 마라.

다음 문제가 발생할 수 있다.

* 잘못된 작가 attribution
* 원문과 다른 번역
* 출처가 없는 가짜 명언
* 저작권 문제
* 서비스 속도 저하
* 외부 사이트 장애
* 중복 콘텐츠
* 부적절한 문맥

검증된 명언 라이브러리를 구축한다.

명언은 관리자 승인 후 사용자에게 노출한다.

명언 데이터는 다음 필드를 포함한다.

```json
{
  "quote_id": "",
  "quote_text_ko": "",
  "original_text": "",
  "author_name": "",
  "work_title": "",
  "publication_info": "",
  "source_url": "",
  "source_type": "",
  "translator": "",
  "language": "",
  "themes": [],
  "emotional_tone": [],
  "suitable_states": [],
  "unsuitable_states": [],
  "rights_status": "",
  "verification_status": "",
  "attribution_confidence": 0.0,
  "reviewed_by": "",
  "reviewed_at": "",
  "active": true
}
```

`rights_status` 예시:

* public_domain
* licensed
* permission_granted
* internally_written
* review_required
* prohibited

`verification_status` 예시:

* primary_source_verified
* reputable_secondary_verified
* translation_verified
* unverified
* rejected

사용자 노출 조건:

* active = true
* rights_status가 허용 상태
* verification_status가 검증 상태
* attribution_confidence가 기준 이상
* 금지된 건강·자해·공포 콘텐츠가 없음

출처가 불확실하면 유명인 이름을 붙이지 마라.

# 12. 명언 RAG 구조

명언 검색에는 RAG 또는 하이브리드 검색을 사용할 수 있다.

이는 RAG가 적합한 사용처다.

하지만 RAG는 검증된 명언 라이브러리 안에서만 검색해야 한다.

허용 흐름:

```text
오늘 기록과 핵심 키워드
→ 검색용 임베딩 및 메타데이터 필터
→ 검증된 명언 후보 검색
→ 규칙 기반 안전 필터
→ 후보 점수 계산
→ 최종 명언 선택
```

금지 흐름:

```text
오늘 기록
→ 인터넷 전체 검색
→ 출처 확인 없이 첫 문장을 사용자에게 노출
```

검색은 다음을 결합한다.

* 의미 유사도
* 키워드 일치
* 감정 톤
* 적합 상태
* 부적합 상태 제외
* 저작권 상태
* 출처 신뢰도
* 최근 노출 여부
* 사용자 선호

RAG가 실제 명언 문구를 생성하거나 수정하면 안 된다.

명언 원문은 검증된 라이브러리 값을 그대로 사용한다.

---

# 13. 명언 선택 점수

명언 후보 q의 초기 점수:

```text
QuoteScore(q)
=
주제 적합도 30%
+ 오늘 일기 상태 적합도 25%
+ 감정 톤 적합도 15%
+ 오늘 질문·운세 연관성 10%
+ 출처 신뢰도 10%
+ 새로움 10%
- 부적합 상태 패널티
- 최근 반복 패널티
- 과도한 감정 강도 패널티
```

다음 상황에서는 지나치게 긍정적인 명언을 피한다.

* 슬픔이 매우 높음
* 질병·통증 기록
* 갈등 직후
* 큰 실수나 사고 기록
* 심한 지침
* 직접 입력과 텍스트 상태가 크게 불일치

예를 들어 힘든 기록 뒤에 “모든 것은 마음먹기 나름이다” 같은 문구를 보여주면 감정을 무시하는 경험이 될 수 있다.

힘든 날에는 문제 해결보다 인정과 동행을 담은 명언을 우선한다.

좋은 날에는 확장, 감사, 용기, 관계, 새로운 시작과 관련된 명언을 우선한다.

# 14. 실제 명언이 없을 때의 폴백

조건을 만족하는 검증된 실제 명언이 없으면 다음 중 하나를 사용한다.

1. 안전하게 검증된 일반 명언
2. 사용자가 최근 보지 않은 중립적 명언
3. 앱이 직접 생성한 “오늘의 문장”

앱이 생성한 문장은 실제 인물이나 책의 문장처럼 표시하면 안 된다.

다음처럼 명확히 표시한다.

* 오늘의 문장
* 오늘의 기록에서 만든 문장
* 앱이 오늘의 마음을 담아 쓴 문장

예:

“오늘 버틴 마음도 오늘 살아낸 하루의 일부예요.”

이 경우 작가명 대신 다음 중 하나를 표시한다.

* 오늘의 기록에서
* 앱이 건넨 문장
* 나를 위한 오늘의 문장

유명인 이름을 임의로 생성하거나 붙이지 마라.

# 15. 명언 UI

일기 저장 직후 다음 순서로 보여준다.

1. 저장 완료 표시
2. 짧은 전환 애니메이션
3. 오늘의 명언 또는 오늘의 문장
4. 작가와 출처
5. 저장 버튼
6. 공유 버튼
7. 선택적 만족도 버튼

명언 카드가 일기 저장을 방해해서는 안 된다.

일기 저장 API가 성공한 뒤 명언 검색이 실패하더라도 일기 저장은 성공 상태를 유지한다.

명언 검색 실패 시 폴백 문장을 제공한다.

사용자가 명언을 나중에 다시 볼 수 있도록 일기 상세 화면에 함께 저장한다.

명언 변경 기능은 기본적으로 제공하지 않는다.

반복해서 새 명언을 뽑는 행동이 콘텐츠의 의미를 약화시킬 수 있기 때문이다.

필요하다면 “다른 문장 보기”를 하루 1회 정도로 제한하고 이벤트를 저장한다.

# 16. 명언 피드백

선택적으로 다음 반응을 수집한다.

* 마음에 남아요
* 괜찮아요
* 나와 맞지 않아요

추가 행동 데이터:

* 명언 저장
* 공유
* 다시 보기
* 일기 상세에서 재확인
* 다른 문장 요청
* 출처 열기

명언 추천 모델은 클릭만 최적화하지 않는다.

다음 보상값을 결합한다.

* 명시적 만족도
* 저장
* 재확인
* 공유
* 다른 문장 요청 여부
* 부정 피드백
* 최근 반복 여부

감정적으로 과장된 문구가 공유율만 높인다는 이유로 반복 노출되지 않게 한다.

# 17. 콘텐츠 간 일관성과 다양성

오늘의 질문, 오늘의 운세, 오늘의 명언이 모두 똑같은 말을 반복하면 안 된다.

각 콘텐츠의 역할을 분리한다.

## 오늘의 질문

사용자가 스스로 생각하게 한다.

예:

“오늘 꼭 책임지지 않아도 되는 일 한 가지는 무엇인가요?”

## 오늘의 운세

왜 그런 주제가 중요한지 여러 생활 영역에서 설명한다.

예:

“오늘은 새로운 일을 더 맡기보다 이미 가진 책임의 우선순위를 정리할수록 흐름이 편안해질 수 있습니다.”

## 오늘의 명언

기록을 마친 감정을 따뜻하게 닫는다.

예:

“쉼은 멈춤이 아니라 다시 나아가기 위한 리듬이다.”

세 콘텐츠의 키워드는 연결되지만 문장과 기능은 달라야 한다.

콘텐츠 간 의미 중복도를 계산하고 기준 이상이면 다시 생성하거나 다른 명언을 선택한다.

# 18. 콘텐츠 히스토리와 반복 방지

다음 기록을 사용자별로 저장한다.

* 최근 질문 주제
* 최근 질문 방식
* 최근 운세 헤드라인
* 최근 운세 영역별 핵심 문장
* 최근 명언
* 최근 작가
* 최근 책 또는 출처
* 최근 콘텐츠 감정 톤

초기 반복 제한:

* 동일 명언: 최소 180일간 재노출 금지
* 동일 작가: 최근 7일 내 최대 1회
* 동일 출처: 최근 14일 내 최대 1회
* 같은 질문 핵심 주제: 최근 3일 패널티
* 같은 질문 방식: 최근 2일 패널티
* 같은 운세 헤드라인 의미: 최근 7일 패널티

사용자에게 잘 맞는 주제가 반복되더라도 관점을 바꾼다.

예:

* 인식
* 원인
* 선택
* 행동
* 관계
* 의미
* 회복

# 21. 생성 및 캐싱 시점

사용자의 시간대를 기준으로 날짜를 계산한다.

오늘의 질문과 오늘의 운세는 다음 중 하나로 생성한다.

* 사용자가 처음 앱을 열 때 지연 생성
* 사용자 현지 날짜가 바뀐 뒤 사전 생성
* 두 방식을 결합

동일 날짜에는 동일한 기본 질문과 운세를 유지한다.

사용자가 상태를 입력하거나 수정했다는 이유로 오늘 질문과 오늘 운세를 다시 생성하지 않는다.

운영자가 규칙 오류를 수정한 특별한 경우에만 관리자 재생성 기능을 제공하고 감사 로그를 남긴다.

오늘의 명언은 일기 저장 후 한 번 선택한다.

일기 수정 시 기본적으로 명언을 자동 교체하지 않는다.

사용자가 일기를 크게 수정한 경우에도 기존 명언을 유지하고, 운영 정책에 따라 선택적으로 재선정할 수 있게 기능 플래그로 분리한다.

# 22. 만족도와 장기 사용 지표

단순 체류시간이나 클릭률만 최적화하지 않는다.

핵심 지표:

* 오늘의 질문 노출 후 상태 체크 시작률
* 상태 체크 완료율
* 일기 작성 시작률
* 일기 작성 완료율
* 질문 적합도
* 운세 적합도
* 운세 영역별 열람률
* 명언 만족도
* 명언 저장률
* 7일 기록 지속률
* 30일 기록 지속률
* 주간 평균 기록 일수
* 반복 콘텐츠 불만
* 알림 차단률
* 앱 삭제 또는 계정 삭제 전 행동
* 부정 피드백률

사용자를 과도한 알림이나 불안 자극으로 붙잡지 마라.

장기 사용은 다음 경험으로 만든다.

* 기록이 쌓이며 개인화가 실제로 달라짐
* 과거의 나와 비교할 수 있음
* 질문이 반복되지 않음
* 운세가 단정적이지 않고 실용적임
* 일기 저장 후 감정적 보상이 있음
* 앱이 나를 판단하지 않고 이해해준다는 느낌

# 24. RAG와 Ridge 최종 역할

## 사주 RAG

유지하되 온라인 핵심 판단 경로에서는 제외한다.

역할:

* 이론 문서 검색
* 규칙 근거 검색
* 관리자 검토
* 규칙 작성 보조

## 명언 RAG

유지하고 적극적으로 사용할 수 있다.

단, 검증된 내부 명언 라이브러리만 검색한다.

## Ridge

새 시스템과 비교하는 섀도 기준 모델로만 유지한다.

새 시스템이 충분한 데이터에서 더 안정적이고 정확하다는 것이 확인되면 제거한다.

명언 검색과 Ridge는 서로 관련 없는 모듈로 분리한다.

# 29. 완료 조건

다음 조건을 모두 만족해야 한다.

* 기존 오늘의 질문 알고리즘이 유지된다.
* 질문과 운세가 동일한 공통 컨텍스트를 사용한다.
* 오늘의 질문은 한 가지 핵심 주제로 축약된다.
* 오늘의 운세는 종합·일·관계·재물·건강으로 분리된다.
* 운세가 미래 사건을 단정하지 않는다.
* 오늘의 상태 입력이 오늘 질문과 운세에 누수되지 않는다.
* 콘텐츠 노출 시점이 기록된다.
* 일기 저장 후 명언 또는 오늘의 문장이 제공된다.
* 명언의 작가와 출처가 검증된다.
* 검증되지 않은 명언은 사용자에게 노출되지 않는다.
* 저작권 상태가 관리된다.
* 명언 RAG는 내부 검증 라이브러리만 검색한다.
* 적합한 실제 명언이 없으면 앱 생성 문장으로 안전하게 대체된다.
* 앱 생성 문장은 실제 인물에게 귀속되지 않는다.
* 질문·운세·명언의 의미가 연결되지만 서로 반복되지 않는다.
* 기존 UI를 재사용할 수 있으면 유지한다.
* 더 효율적인 UI가 명확하면 근거를 제시하고 수정하거나 재설계한다.
* 일기 저장과 명언 생성 실패가 분리된다.
* 관리자 화면에서 모든 근거와 버전을 확인할 수 있다.
* RAG와 Ridge의 역할이 명확히 분리된다.
* 주요 단위·통합·안전·데이터 누수 테스트가 통과한다.

먼저 현재 코드베이스에서 오늘의 운세와 오늘의 명언 기능의 존재 여부, 데이터 구조, UI 위치, 외부 명언 수집 코드, RAG 재사용 가능성을 분석하라.

코드를 즉시 변경하지 말고 분석 결과와 단계별 구현 계획을 먼저 보고하라.

# 오늘의 문장 생성 정책 확정

검증된 실제 명언이 오늘의 기록과 충분히 어울리지 않거나, 출처·저작권·작가 귀속을 신뢰할 수 없는 경우에는 억지로 실제 명언을 보여주지 않는다.

이때 사용자의 오늘 기록을 바탕으로 앱이 직접 작성한 **“오늘의 문장”**을 제공한다.

오늘의 문장은 단순한 오류 폴백이 아니라, 실제 명언과 동등한 정식 콘텐츠 유형으로 취급한다.

---

## 1. 콘텐츠 선택 우선순위

일기 저장 후 다음 순서로 콘텐츠를 선택한다.

1. 오늘 기록과 잘 맞고 출처가 검증된 실제 명언
2. 오늘 기록과 어느 정도 맞는 안전한 범용 명언
3. 앱이 오늘 기록을 바탕으로 작성한 오늘의 문장
4. LLM 생성 실패 시 검수된 템플릿 문장

실제 명언의 출처 신뢰도나 문맥 적합도가 낮다면 2번보다 3번을 우선해도 된다.

유명한 명언을 보여주는 것보다 오늘 사용자에게 자연스럽게 맞는 문장을 제공하는 것을 우선한다.

---

## 2. 오늘의 문장 생성 입력

오늘의 문장은 일기 저장 후 다음 데이터를 사용해 생성한다.

* 오늘의 질문 핵심 키워드
* 오늘의 질문 보조 긴장 키워드
* 오늘의 종합운 핵심 주제
* 사용자가 입력한 행복도
* 선택한 기분
* 핵심 상태값
* 생활 영역 상태
* 사건 태그
* 자유 일기 텍스트 특징
* 직접 입력과 텍스트 추정의 차이
* 최근 제공한 오늘의 문장
* 사용자가 선호한 문장 톤

사주 원국이나 오늘 일주의 전문 용어를 문장에 직접 노출하지 않는다.

사주와 일주 정보는 오늘의 질문과 운세를 통해 이미 추상화된 핵심 주제만 사용한다.

---

## 3. 오늘의 문장 역할

오늘의 문장은 다음 목적을 가진다.

* 일기를 쓴 사용자의 감정을 인정한다.
* 오늘 하루를 판단하지 않고 받아준다.
* 기록을 마쳤다는 정서적 마무리를 제공한다.
* 지나치게 교훈적이거나 훈계하는 말을 피한다.
* 사용자가 다시 읽고 싶은 짧은 여운을 남긴다.

오늘의 문장은 사용자의 문제를 해결하려는 조언문이 아니다.

오늘의 질문이 생각을 시작하게 하고, 오늘의 운세가 흐름을 설명한다면, 오늘의 문장은 하루를 따뜻하게 닫는 역할을 한다.

---

## 4. 문장 생성 규칙

오늘의 문장은 기본적으로 한 문장으로 작성한다.

필요한 경우 최대 두 문장까지 허용한다.

권장 길이:

* 한국어 기준 20~65자
* 최대 100자 이내

권장 톤:

* 따뜻함
* 차분함
* 담백함
* 감성적이지만 과장되지 않음
* 사용자의 감정을 존중함

금지 사항:

* 실제 작가나 유명인의 이름을 붙이는 것
* 책 또는 영화에서 가져온 문장처럼 위장하는 것
* 사용하지 않은 인용부호로 실제 인용문처럼 표현하는 것
* 운명이나 미래를 단정하는 것
* 사용자의 실제 감정을 앱이 더 잘 안다고 주장하는 것
* 사용자의 상태를 진단하는 것
* 억지 긍정
* 죄책감 유발
* 감정을 축소하는 표현
* 지나친 교훈
* 명령형 표현의 반복
* “힘내”, “긍정적으로 생각해” 같은 단순한 위로
* 질병, 사고, 관계 파탄, 재물 손실을 암시하는 표현

---

## 5. 상태별 생성 방향

### 힘든 날

슬픔, 지침, 불안, 질병·통증, 갈등, 실수·사고 등이 높은 경우에는 문제 해결보다 감정의 인정과 동행을 우선한다.

좋은 예:

* 오늘 견뎌낸 마음도 충분히 기록될 가치가 있어요.
* 다 정리되지 않은 마음도 오늘의 나로 남아도 괜찮아요.
* 잠시 멈춘 하루에도 나름의 속도와 의미가 있어요.

피해야 할 예:

* 모든 일은 잘될 거예요.
* 시련은 성공을 위한 과정입니다.
* 마음먹기에 따라 행복해질 수 있어요.

### 평온한 날

안정, 평온, 무덤덤, 특별한 일 없음 등이 중심이면 작은 일상의 의미를 살린다.

좋은 예:

* 큰일이 없었던 하루도 마음이 머문 자리로 남아요.
* 조용한 하루는 내 마음의 숨을 고르는 시간이었어요.

### 좋은 날

기쁨, 설렘, 성과·칭찬, 소개·만남, 새로운 시작 등이 중심이면 기쁨의 확장과 기억을 돕는다.

좋은 예:

* 오늘 피어난 기쁨은 오래 기억해도 좋은 마음이에요.
* 설레는 마음이 오늘의 나를 한 걸음 넓혀주었어요.

### 과부하가 있는 날

성과는 높지만 에너지와 회복이 낮거나 업무 압박이 강한 경우에는 성취와 소진을 동시에 인정한다.

좋은 예:

* 잘해낸 하루일수록 나를 돌보는 시간도 함께 필요해요.
* 오늘의 성취 뒤에 애쓴 마음까지 잊지 않아도 돼요.

### 감정 불일치가 큰 날

직접 입력과 일기 텍스트의 분위기가 크게 다르면 어느 한쪽이 진실이라고 단정하지 않는다.

좋은 예:

* 한마디로 정리되지 않는 마음도 오늘의 진짜 모습일 수 있어요.
* 괜찮음과 힘듦이 함께 있었던 하루여도 괜찮아요.

---

## 6. 표시 방식

앱이 생성한 문장은 반드시 다음 중 하나의 제목으로 표시한다.

* 오늘의 문장
* 오늘의 기록에서 만든 문장
* 오늘의 마음을 담은 문장

작가 영역에는 사람 이름을 표시하지 않는다.

대신 다음과 같이 표시할 수 있다.

* 오늘의 기록에서
* 나를 위한 오늘의 문장
* 앱이 건넨 문장

권장 UI:

```text
오늘의 문장

“잘해낸 하루일수록 나를 돌보는 시간도 함께 필요해요.”

오늘의 기록에서
```

실제 명언과 오늘의 문장이 시각적으로 구분되도록 한다.

실제 명언:

```text
오늘의 명언
명언 내용
작가 · 작품명
```

앱 생성 문장:

```text
오늘의 문장
생성 문장
오늘의 기록에서
```

---

## 7. 생성 결과 저장

오늘의 문장은 다음 데이터를 저장한다.

```json
{
  "content_type": "app_original_sentence",
  "sentence_text": "",
  "source_label": "오늘의 기록에서",
  "generation_context": {
    "primary_keyword": "",
    "secondary_keyword": "",
    "dominant_emotions": [],
    "event_tags": [],
    "state_summary": ""
  },
  "prompt_version": "",
  "model_version": "",
  "safety_filter_version": "",
  "generated_at": "",
  "selection_reason": ""
}
```

일기 원문 전체를 `generation_context`나 일반 로그에 복사하지 않는다.

문장 생성에 사용한 핵심 특징과 코드만 저장한다.

---

## 8. LLM 출력 형식

LLM에는 다음과 같은 구조화된 입력만 제공한다.

```json
{
  "primary_theme": "회복",
  "secondary_theme": "책임조절",
  "emotions": ["지침", "평온"],
  "state_summary": "성과는 유지했지만 최근 에너지가 낮아짐",
  "event_tags": ["업무 압박"],
  "discrepancy_level": "low",
  "tone": "따뜻하고 담백함",
  "recent_sentences": [
    "오늘의 마음도 천천히 자리를 찾고 있어요."
  ],
  "constraints": [
    "한 문장",
    "20자에서 65자",
    "실제 인용문처럼 작성하지 않음",
    "유명인 이름을 사용하지 않음",
    "사주 용어를 노출하지 않음",
    "운명을 단정하지 않음",
    "감정을 판단하지 않음",
    "억지 긍정을 사용하지 않음",
    "최근 문장과 의미를 반복하지 않음"
  ]
}
```

LLM 출력은 다음 스키마를 강제한다.

```json
{
  "sentence": "잘해낸 하루일수록 나를 돌보는 시간도 함께 필요해요.",
  "tone": "gentle",
  "themes": ["회복", "책임조절"]
}
```

LLM이 설명, 작가명, 출처, 해설을 추가하지 못하게 한다.

## 9. 품질 검증

생성된 문장은 사용자에게 노출하기 전에 다음 검사를 통과해야 한다.

* 길이 제한
* 금지 표현
* 실제 인용문 오인 가능성
* 유명인 및 작가명 포함 여부
* 사주 전문 용어 포함 여부
* 의학적 또는 심리적 진단
* 미래 단정
* 폭력·자해·죽음 미화
* 억지 긍정
* 최근 문장과의 의미 중복
* 오늘의 질문 및 운세와의 과도한 문장 중복
* 사용자 상태와 반대되는 감정 강요

검사에 실패하면 한 번 다시 생성한다.

재생성도 실패하면 검수된 템플릿 문장을 제공한다.

## 10. 검수된 템플릿 폴백

다음과 같은 템플릿 풀을 운영자가 관리할 수 있게 한다.

### 회복

* 오늘 애쓴 마음도 이제 잠시 쉬어가도 괜찮아요.
* 멈춰 있는 시간에도 마음은 천천히 회복하고 있어요.

### 안정

* 모든 마음을 오늘 안에 정리하지 않아도 괜찮아요.
* 천천히 가라앉는 마음에도 저마다의 시간이 필요해요.

### 감정인식

* 이름 붙이기 어려운 마음도 오늘의 나로 남아도 괜찮아요.
* 여러 감정이 함께 있었던 하루도 충분히 진짜예요.

### 관계

* 누군가를 생각한 마음만큼 내 마음도 함께 살펴봐 주세요.
* 가까워지는 마음과 거리를 두는 마음 모두 나를 지키는 방식이에요.

### 실행

* 오늘의 작은 움직임도 내일의 방향을 만들고 있어요.
* 완벽하지 않은 시작도 분명한 한 걸음이에요.

### 성취

* 오늘 이룬 것 뒤에는 오래 애쓴 마음이 함께 있었어요.
* 결과뿐 아니라 그곳까지 온 나도 기억해 주세요.

템플릿은 반복 방지를 위해 충분한 수량을 확보하고 버전 관리한다.

## 11. 반복 방지

앱 생성 문장은 사용자별로 다음 반복 제한을 적용한다.

* 동일 문장: 최소 180일 동안 재사용 금지
* 의미가 매우 비슷한 문장: 최근 30일 패널티
* 동일한 문장 구조: 최근 7일 패널티
* 동일 핵심 키워드: 반복 가능하나 관점을 변경
* 같은 종결 표현의 연속 사용 제한

예:

* “괜찮아요”로 끝나는 문장이 연속으로 나오지 않게 한다.
* “오늘의 ~도” 구조를 반복하지 않는다.
* 회복 주제가 반복되면 인정, 경계, 행동, 의미 등 관점을 순환한다.

## 12. 피드백과 개인화

오늘의 문장에 다음 선택적 피드백을 제공한다.

* 마음에 남아요
* 괜찮아요
* 나와 맞지 않아요

추가 행동:

* 저장
* 공유
* 다시 보기
* 일기 상세에서 재확인
* 다른 문장 요청

사용자별로 다음 선호를 학습한다.

* 짧고 담백한 문장
* 감성적인 문장
* 위로 중심
* 성찰 중심
* 용기 중심
* 행동을 부드럽게 암시하는 문장
* 비유가 있는 문장
* 비유가 없는 직접적인 문장

사용자가 문장 톤을 직접 설정할 수 있는 옵션은 향후 기능으로 분리한다.

명언이나 문장의 부정 피드백은 오늘 질문이나 운세의 핵심 알고리즘 전체가 틀렸다는 뜻으로 처리하지 않는다.

콘텐츠별 피드백을 독립적으로 학습한다.

## 13. API 실패 처리

일기 저장과 오늘의 문장 생성은 별도의 작업으로 처리한다.

일기 저장이 성공하면 문장 생성 실패 여부와 관계없이 성공 응답을 유지한다.

문장 생성 순서:

1. 실제 명언 후보 검색
2. 적합한 명언이 없으면 오늘의 문장 생성
3. 생성 실패 시 재시도
4. 재시도 실패 시 템플릿 폴백

사용자가 빈 화면이나 오류 메시지만 보지 않게 한다.

## 14. 완료 조건

다음 조건을 모두 만족해야 한다.

* 적절한 실제 명언이 없을 때 오늘의 문장이 제공된다.
* 오늘의 문장은 정식 콘텐츠 유형으로 저장된다.
* 실제 작가나 책의 문장처럼 위장하지 않는다.
* 사주 용어와 운명 단정이 없다.
* 일기 원문을 일반 로그에 저장하지 않는다.
* 직접 입력과 일기 상태를 모두 고려한다.
* 힘든 상태에서 억지 긍정을 피한다.
* 최근 문장과의 반복을 방지한다.
* LLM 실패 시 안전한 템플릿이 제공된다.
* 일기 저장은 문장 생성 실패와 독립적으로 성공한다.
* 문장 피드백이 질문·운세 피드백과 분리되어 저장된다.
* 관리자 화면에서 생성 근거, 모델 버전, 필터 결과를 확인할 수 있다.
